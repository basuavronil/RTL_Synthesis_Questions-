### FAQ: What happens with an incomplete sensitivity list in a combinational block?

An incomplete sensitivity list occurs in an `always @(*)` or `always @(a, b)` block when a signal used in the combinational logic is accidentally omitted from the sensitivity list (more common in legacy Verilog `always @(a)` styles).

#### 1. What Warning Do Tools Give?
* **Linter & Compiler Warnings:** EDA tools will flag this with messages such as *`Incomplete sensitivity list`*, *`Combinational logic infers latches`*, or *`Signal is read in block but not present in sensitivity list`*.

#### 2. Synthesis Behavior
* **Synthesis Ignores the List:** Modern synthesis tools automatically infer full combinational logic for `always @(*)` blocks. If explicit signal lists are used, synthesis tools typically treat them as a hint or reconstruct the combinatorial dependency graph based on the logic inside, synthesizing the full combinational circuit regardless of omissions.

#### 3. Simulation Behavior (The Simulation-Synthesis Mismatch)
* **Missing Events:** Traditional event-driven simulators rely strictly on the sensitivity list to trigger evaluation. If a signal changes value but is *missing* from the sensitivity list, the simulator will **not** re-evaluate the block, causing the simulation waveform to hold an outdated value.
* **The Hazard:** This creates a dangerous **simulation-synthesis mismatch**, where your simulation passes successfully due to missed updates, but the synthesized hardware behaves completely differently in silicon.

> **Best Practice:** Always use **`always_comb`** (in SystemVerilog) or **`always @(*)`** (in Verilog-2001 and later) to let the tool automatically manage sensitivity lists and prevent these mismatches entirely.
