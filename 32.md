# FAQ & Design Pitfalls: Unused States & Inferred Latches in FSMs

## Question: What happens to unused states in an FSM?
**Answer:** They cause lockup unless you add a default transition to idle or use safe-FSM synthesis options. Moreover, omitting a catch-all branch in combinational logic forces the synthesis tool to infer dangerous **latches**.

---

## 1. Why Unused States Exist
* **One-Hot FSMs:** For an $N$-state machine, you have $2^N$ possible bit combinations, but only $N$ are valid (e.g., a 5-state machine has 32 total combinations, but 27 are illegal).
* **Binary / Gray FSMs:** If you have 5 states, you need 3 bits ($2^3 = 8$ combinations), leaving **3 unused states** (`101`, `110`, `111`).

If a transient glitch, noise spike, or single-event upset (SEU) flips a register bit, the FSM can land directly in one of these dead zones.

---

## 2. What Happens in Hardware? (Inferred Latches & Lockup)

Depending on how your RTL is written (especially in `case` statements), synthesis tools will typically handle missing states in one of two ways:
* **Inferred Latches:** If you omit a catch-all `default` branch in a combinational next-state decoding block (such as an `always_comb` block), the synthesis tool assumes the output must hold its value for any unhandled states. Because combinational logic cannot natively store state without feedback, the tool is forced to **infer a transparent latch**.
* **FSM Lockup / Self-Loops:** If unassigned paths resolve to hold states or `X` values, the FSM can permanently lock up or exhibit corrupted control signals in hardware.

### Why Inferred Latches are Dangerous:
* **Asynchronous Behavior:** Latches are level-sensitive, breaking strict synchronous design methodologies.
* **Timing Closure Nightmares:** Static timing analysis (STA) tools struggle with transparent latches, causing complex setup/hold violations.
* **Simulation Mismatches:** RTL simulators may handle unassigned conditions differently than physical gates, hiding bugs until post-synthesis or silicon testing.

---

## 3. How to Prevent FSM Lockup & Latches

### Strategy A: Explicit Default Assignment & Catch-All Case
Always assign a default value at the top of your combinational block and include an explicit `default:` case that routes back to `IDLE` or a reset state:

```verilog
always_comb begin
    next_state = current_state; // Prevents inferred latches
    case (current_state)
        IDLE:    if (start) next_state = RUN;
        RUN:     if (done)  next_state = IDLE;
        default: next_state = IDLE; // Catch-all for illegal states
    endcase
end
