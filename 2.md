# Why Use Blocking (`=`) Assignments in Combinational `always` Blocks?

**⚠️ Note: Using non-blocking (`<=`) in a combinational `always` block will NOT give a synthesis error (or usually even a compile error). Synthesis tools still infer the same combinational logic, so the design can look fine in hardware. The problems show up in simulation: stale reads, delta-cycle glitches, and possible simulation vs. synthesis mismatch.**

> **TL;DR:** Combinational logic has no memory and no clock. Its outputs must follow its inputs immediately. Blocking assignments update in the order the code is written, which matches how a chain of gates behaves.

## The Rule

| Logic Type | Block | Assignment |
|---|---|---|
| Combinational | `always @(*)` / `always_comb` | Blocking `=` |
| Sequential | `always @(posedge clk)` / `always_ff` | Non-blocking `<=` |

---

## 1. Blocking Matches the Hardware

A combinational path is just wires and gates. If `t = a & b` and `y = t | c`, then `y` depends on the **new** value of `t` right away.

Blocking assignments model this: each line updates its variable immediately, so the next line sees the fresh value.

```verilog
always @(*) begin
    t = a & b;    // t updates immediately
    y = t | c;    // y uses the NEW t
end
```

---

## 2. What Goes Wrong With Non-Blocking

**It will not cause a synthesis error.** The tool still builds the same AND/OR gates. The issue is in simulation:

```verilog
always @(*) begin
    t <= a & b;   // t updates later, in the NBA region
    y <= t | c;   // y is computed from the OLD t
end
```

When `a` changes:

1. `y` is first computed from the **old** `t`.
2. `t` then updates in the NBA region, which re-triggers the block.
3. `y` is recomputed in a **later delta cycle**.

The final value usually settles correctly, but you get:

- A **transient wrong value** on `y` (a delta-cycle glitch in simulation)
- Possible **stale reads** if a testbench or another block samples `y` at the wrong moment
- **Extra simulator work** from re-evaluating the block
- A possible **simulation vs. synthesis mismatch**, because simulation shows the delayed behavior while the synthesized hardware has none

---

## 3. Statement Order Works Like Data Flow

With blocking assignments you write logic top to bottom, following the signal path, and it behaves as you read it. This makes intermediate variables (like `t`) safe to use inside the block.

---

## 4. Why the Rule Differs by Block Type

| | Sequential (`posedge clk`) | Combinational (`always @(*)`) |
|---|---|---|
| **Goal** | All flops sample old values, then update together | Outputs follow inputs immediately |
| **Correct choice** | `<=` (update deferred to NBA region) | `=` (update immediate) |
| **Risk if wrong** | Race conditions between blocks | Stale values, extra delta cycles |
| **Synthesis error if wrong?** | **No** | **No** |

---

## 5. Best Practices

- Use `always @(*)` (or `always_comb` in SystemVerilog) with `=` for combinational logic.
- Assign a **default value** to every output, or cover every branch, to avoid unintended **latches**.
- **Never mix** `=` and `<=` on the same signal or in the same block.
- Don't rely on the synthesis tool to catch mistakes here. It won't. Use lint tools (Verilator, SpyGlass, Questa Lint) to flag them.

```verilog
// Good: defaults prevent latches
always_comb begin
    y = 1'b0;             // default
    if (sel) y = a & b;
end
```

---

## Interview Answer

> "Blocking assignments update immediately and in order, so intermediate values in a combinational block propagate like real gates. Non-blocking would defer updates to the NBA region, causing stale reads and extra delta-cycle re-evaluation. It won't produce a synthesis error, which is exactly why it's dangerous: the mistake only shows up as simulation behavior."

---

## Summary

| Rule | Assignment | Context | Reason |
|---|---|---|---|
| Combinational logic | Blocking `=` | `always @(*)` | Immediate propagation within the same delta cycle |
| Sequential logic | Non-blocking `<=` | `always @(posedge clk)` | Avoids races; models flip-flop sampling |
| Mixed assignments | Never mix | Same block / signal | Avoids races and undefined tool behavior |
