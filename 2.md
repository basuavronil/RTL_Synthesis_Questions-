# Why use blocking (=) in combinational always blocks? 

## The Golden Rule

| Logic Type | Assignment to Use | Block Type |
|---|---|---|
| Sequential (clocked) | Non-blocking `<=` | `always @(posedge clk)` |
| Combinational | Blocking `=` | `always @(*)` |
| Mixed | **Never mix** in the same `always` block or on the same signal | - |

Mixing them inside a clocked block does **not** cause a compiler or synthesis error, but it creates dangerous mismatches between how the design **simulates** and how it **behaves in hardware**.

---

## 1. How Event Scheduling Works (The Root Cause)

Verilog event-driven simulators divide each time step into several execution regions:

- **Active Region:** Evaluates the right-hand side (RHS) of assignments and executes blocking (`=`) assignments immediately.
- **NBA (Non-Blocking Assignment) Region:** Updates the left-hand side (LHS) of non-blocking (`<=`) assignments whose RHS values were evaluated in the Active region.

**Blocking (`=`):** Executes sequentially in the Active region. Later lines in the block wait until the variable has been updated, and the update is immediate.

**Non-blocking (`<=`):** Evaluates the RHS in the Active region using the values at the clock edge, but schedules the LHS update for later, in the NBA region.

---

## 2. Why Blocking (`=`) in Clocked Blocks Causes Race Conditions

Two flip-flops in series (a shift register or pipeline stage):

```verilog
// Flop 1
always @(posedge clk) begin
    q1 = d;    // Blocking assignment
end

// Flop 2
always @(posedge clk) begin
    q2 = q1;   // Blocking assignment
end
```

### The race condition

At `posedge clk`, both `always` blocks are scheduled in the Active region. The execution order of independent `always` blocks at the same timestamp is **nondeterministic**:

- **Scenario A (Flop 1 first):** `q1` updates immediately to `d`. Flop 2 then reads the *new* `q1`, so both flops hold `d` after one clock cycle.
- **Scenario B (Flop 2 first):** `q2` reads the *old* `q1` before it updates, so `d` takes two clock cycles to reach `q2`.

Depending on the simulator, compile flags, or even small edits elsewhere, the simulation behavior can change randomly.

---

## 3. How Non-Blocking (`<=`) Eliminates the Race

```verilog
// Flop 1
always @(posedge clk) begin
    q1 <= d;   // Non-blocking assignment
end

// Flop 2
always @(posedge clk) begin
    q2 <= q1;  // Non-blocking assignment
end
```

### What happens at `posedge clk`

1. **Active Region (evaluation):** The RHS of both blocks is evaluated using values from just before the clock edge.
   - Flop 1 evaluates `d`
   - Flop 2 evaluates `q1` (the **old** value)
2. **NBA Region (update):** Both LHS variables are updated together.
   - `q1` receives `d`
   - `q2` receives the old value of `q1`

No matter which block is evaluated first, Flop 2 always captures the old `q1`. This matches real flip-flop behavior (setup/hold constraints and propagation delays).

---

## 4. Why Synthesis Tools Accept It Without Errors

Synthesis tools (AMD Vivado, Synopsys Design Compiler, Cadence Genus) infer hardware from **data flow and edge sensitivity**, not from event-queue execution order.

- `always @(posedge clk)` makes the tool infer flip-flops clocked by `clk`.
- Physical flip-flops have an intrinsic propagation delay (t<sub>co</sub>), so they sample their input *before* their output changes.
- The tool therefore infers a **two-stage shift register** for *both* code snippets.

| Environment | Blocking (`=`) Code | Non-Blocking (`<=`) Code |
|---|---|---|
| **Synthesis / Hardware** | Infers 2 sequential flip-flops | Infers 2 sequential flip-flops |
| **Simulation** | Race condition (acts like 1 or 2 flops randomly) | Deterministic (always acts like 2 flops) |

Synthesis produces a two-flop chain, while a blocking-assignment simulation may behave like a single wire. The result is a **simulation vs. synthesis mismatch**: RTL passes its tests, but the hardware behaves differently.

---

## 5. Combinational Logic: Why Blocking (`=`) Is Correct

Inside `always @(*)`, blocking assignments propagate values immediately through successive expressions within the same delta cycle:

```verilog
always @(*) begin
    t = a & b;      // t is updated immediately
    y = t | c;      // y sees the new value of t
end
```

Using `<=` here would delay `t`'s update to the NBA region, so `y` could evaluate with a stale `t`.

---

## Summary Checklist

| Rule | Assignment Type | Target Context | Reason |
|---|---|---|---|
| Sequential logic | Non-blocking `<=` | `always @(posedge clk)` | Prevents simulation races; accurately models physical D-FF sampling |
| Combinational logic | Blocking `=` | `always @(*)` | Ensures immediate signal propagation within the same delta cycle |
| Mixed assignments | Never mix | Same `always` block / signal | Avoids race conditions and undefined tool behavior |
