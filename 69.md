# What does a `for` loop synthesize into?

**Answer:** Replicated (unrolled) logic, not iterative execution.

## Key idea

In software, a loop runs one iteration after another over time. In synthesizable Verilog, the loop is **unrolled at synthesis time**: the tool makes one copy of the hardware for each iteration, and all copies exist side by side in the circuit.

## Example

```verilog
always @(*) begin
    for (i = 0; i < 4; i = i + 1)
        y[i] = a[i] & b[i];
end
```

This does **not** step through `i` over several clock cycles. It becomes **four AND gates** working in parallel:

```verilog
y[0] = a[0] & b[0];
y[1] = a[1] & b[1];
y[2] = a[2] & b[2];
y[3] = a[3] & b[3];
```

## Why this happens

- Hardware has no program counter or instruction sequence.
- The loop bounds must be **constant** and known at compile time, so the tool can determine how many copies to make.
- The loop variable (`i`) is only a synthesis-time index, not a real signal or register.

## Software loop vs. hardware loop

| Aspect | Software loop | Verilog `for` loop (synthesized) |
|---|---|---|
| Execution | Sequential, over time | Parallel, all at once |
| Loop variable | Real runtime variable | Compile-time index only |
| Iteration count | Can be dynamic | Must be fixed (constant bounds) |
| Cost | More iterations = more time | More iterations = more area |

## Common uses

- Bit-wise operations on buses
- Parity or reduction calculations
- Priority encoders
- Generating arrays of registers or gates (also done with `generate for`)

## Things to watch out for

- **Area grows with iteration count.** A loop of 1000 iterations creates 1000 copies of the logic.
- **Long combinational chains.** If each iteration depends on the previous one (e.g., a running sum), the copies chain together and the path delay increases.
- **Non-constant bounds** (such as a loop limit that depends on an input signal) are not synthesizable.
- To get true step-by-step behavior over time, use a **counter and a state machine (FSM)** instead of a loop.

## Summary

A `for` loop in RTL is a **shorthand for writing repeated hardware**, not a sequence of steps. Each iteration becomes its own physical logic, and they all operate concurrently.
