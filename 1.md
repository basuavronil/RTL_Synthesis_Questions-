## The Golden Rule

| Logic Type | Use | Block Style |
|---|---|---|
| Sequential (clocked) | Non-blocking `<=` | `always @(posedge clk)` |
| Combinational | Blocking `=` | `always @(*)` |

```verilog
// Sequential
always @(posedge clk) begin
    q <= d;          // non-blocking
end

// Combinational
always @(*) begin
    y = a & b;       // blocking
end
```

> **Note:** Mixing them up inside a clocked block will **not** trigger a compiler or synthesis error. But it creates dangerous discrepancies between how your design **simulates** and how it **behaves in hardware**.

---

## 1. How Event Scheduling Works (The Root Cause)

Verilog event-driven simulators divide time into discrete **time steps**, and each time step is divided into several **execution regions**:

| Region | What Happens |
|---|---|
| **Active Region** | Evaluates the RHS of assignments and executes blocking (`=`) assignments immediately. |
| **NBA Region** (Non-Blocking Assignment) | Updates the LHS of non-blocking (`<=`) assignments whose RHS values were evaluated earlier in the Active region. |

### Blocking Assignment (`=`)
Executes sequentially in the Active region. It **blocks** execution of subsequent lines in the block until the current assignment updates the variable **immediately**.

### Non-Blocking Assignment (`<=`)
Evaluates the RHS in the Active region using the **current values at the clock edge**, but **schedules the LHS update** to happen later in the NBA region.

```text
 One simulation time step
 ┌──────────────────────────────────────────────────────────┐
 │  Active Region                                           │
 │   • blocking (=) assignments execute & update NOW        │
 │   • RHS of non-blocking (<=) is evaluated (LHS unchanged)│
 ├──────────────────────────────────────────────────────────┤
 │  NBA Region                                              │
 │   • all scheduled (<=) LHS updates happen here           │
 └──────────────────────────────────────────────────────────┘
```

---

## 2. Why Blocking (`=`) in Clocked Blocks Causes Simulation Race Conditions

Consider two edge-triggered flip-flops connected in series (a shift register / pipeline stage):

```verilog
// Flop 1
always @(posedge clk) begin
    q1 = d;    // Blocking assignment
end

// Flop 2
always @(posedge clk) begin
    q2 = q1;   // Blocking assignment
end
```

### The Race Condition

When `posedge clk` occurs, **both** `always` blocks are scheduled to execute in the Active region. Because the execution order between independent `always` blocks at the exact same timestamp is **nondeterministic** in Verilog simulators:

- **Scenario A (Flop 1 executes first):** `q1` updates immediately to `d`. When Flop 2 executes, `q2` reads the **new** `q1`. Both flops hold `d` in a single clock cycle (behaves like 1 flop).
- **Scenario B (Flop 2 executes first):** `q2` reads the **old** `q1` before `q1` updates. `d` properly takes two clock cycles to reach `q2` (behaves like 2 flops).

Depending on the simulator, compile flags, or even minor code edits elsewhere, your simulation behavior can change randomly.

---

## 3. How Non-Blocking (`<=`) Eliminates the Race Condition

Now consider the same design using non-blocking assignments:

```verilog
// Flop 1
always @(posedge clk) begin
    q1 <= d;   // Non-blocking assignment
end

// Flop 2
always @(posedge clk) begin
    q2 <= q1;  // Non-blocking assignment
end
```

### What happens at `posedge clk`

1. **Active Region (Evaluation):** The simulator evaluates the RHS for both blocks using the values existing *just before* the clock edge.
   - Flop 1 evaluates `d`
   - Flop 2 evaluates `q1` (the **old** value of `q1`)
2. **NBA Region (Update):** The simulator updates the LHS for both variables *simultaneously*.
   - `q1` receives the evaluated value of `d`
   - `q2` receives the evaluated **old** value of `q1`

No matter which `always` block evaluates first in the Active region, Flop 2 always captures the old value of `q1`, perfectly matching real hardware flip-flop behavior (setup/hold time constraints and propagation delays).

---

## 4. Why Tools Synthesize It Without Errors

Synthesis tools (AMD Vivado, Synopsys Design Compiler, Cadence Genus) infer hardware based on **data flow and edge sensitivity**, *not* event-queue execution timing.

- When a synthesis tool sees `always @(posedge clk)`, it infers **flip-flops** clocked by `clk`.
- In hardware, physical flip-flops have intrinsic clock-to-output propagation delays (`t_co`). At a clock edge, a flip-flop **samples its input before its output changes**.
- Therefore, the synthesis tool infers a **two-stage shift register for both code snippets**.

| Environment | Blocking (`=`) Code | Non-Blocking (`<=`) Code |
|---|---|---|
| **Synthesis / Hardware** | Infers 2 sequential flip-flops | Infers 2 sequential flip-flops |
| **Simulation** | Race condition (acts like 1 or 2 flops randomly) | Deterministic (acts like 2 flops always) |

Because synthesis produces a two-flop chain while simulation with blocking assignments might act like a single wire/combinational bypass, you get a **Simulation vs. Synthesis Mismatch**: RTL passes tests, but hardware fails or behaves differently.

---

## 5. Combinational Logic: Use Blocking (`=`)

In combinational blocks, you *want* each statement to take effect immediately so later statements see updated values.

```verilog
// Correct: blocking assignments in a combinational block
always @(*) begin
    tmp = a & b;       // tmp updates immediately
    y   = tmp | c;     // sees the NEW tmp
end
```

If you wrongly use `<=` here, `y` would be computed from the **stale** value of `tmp`:

```verilog
// Wrong: non-blocking in a combinational block
always @(*) begin
    tmp <= a & b;      // update deferred to NBA region
    y   <= tmp | c;    // uses the OLD tmp -> glitchy / incorrect in simulation
end
```

## 6. Runnable Testbench: See the Race Yourself

### `shift_blocking.v`  (BAD)

```verilog
module shift_blocking (
    input  wire clk,
    input  wire d,
    output reg  q1,
    output reg  q2
);
    always @(posedge clk) q1 = d;    // blocking
    always @(posedge clk) q2 = q1;   // blocking
endmodule
```

### `shift_nonblocking.v`  (GOOD)

```verilog
module shift_nonblocking (
    input  wire clk,
    input  wire d,
    output reg  q1,
    output reg  q2
);
    always @(posedge clk) q1 <= d;   // non-blocking
    always @(posedge clk) q2 <= q1;  // non-blocking
endmodule
```

### `tb.v`

```verilog
`timescale 1ns/1ps

module tb;
    reg  clk = 0;
    reg  d   = 0;
    wire b_q1, b_q2;   // blocking version
    wire n_q1, n_q2;   // non-blocking version

    shift_blocking    u_bad  (.clk(clk), .d(d), .q1(b_q1), .q2(b_q2));
    shift_nonblocking u_good (.clk(clk), .d(d), .q1(n_q1), .q2(n_q2));

    always #5 clk = ~clk;

    initial begin
        $dumpfile("wave.vcd");
        $dumpvars(0, tb);

        // Drive d away from the clock edge to avoid a TB race of its own
        #2  d = 1;
        #10 d = 0;
        #10 d = 1;
        #30 $finish;
    end

    // $strobe prints AFTER the NBA region, so it shows settled values
    always @(posedge clk)
        $strobe("t=%0t | BAD: q1=%b q2=%b | GOOD: q1=%b q2=%b",
                $time, b_q1, b_q2, n_q1, n_q2);
endmodule
```

### Run it

**Icarus Verilog + GTKWave (free):**

```bash
iverilog -o sim shift_blocking.v shift_nonblocking.v tb.v
vvp sim
gtkwave wave.vcd
```

**Verilator:**

```bash
verilator --binary --timing tb.v shift_blocking.v shift_nonblocking.v
./obj_dir/Vtb
```

### What to expect

- **GOOD (`<=`)**: `q2` always lags `q1` by exactly one clock cycle, on every simulator.
- **BAD (`=`)**: `q2` may equal `q1` in the *same* cycle (behaves like one flop), and this can change with tool, version, or file order.

> Tip: Try swapping the order of the two `always` blocks in `shift_blocking.v` and re-run. Watch the BAD output change while the GOOD output stays identical.

## 7. SystemVerilog: `always_ff` / `always_comb`

SystemVerilog adds intent-declaring blocks that let the tools **check your coding style**:

```systemverilog
// Sequential: use always_ff with non-blocking
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) q <= '0;
    else        q <= d;
end

// Combinational: use always_comb with blocking
always_comb begin
    y = a & b;
end
```

Benefits:

- `always_comb` has an **automatic sensitivity list** (no more forgotten signals in `@(...)`).
- `always_comb` and `always_ff` let linters and synthesis tools **warn about latches** and wrong-style assignments.
- Tools can flag a variable being driven from multiple procedural blocks.

**Recommendation:** in SystemVerilog projects, prefer `always_ff` and `always_comb` over plain `always`.

## 8. Common Pitfalls

### Pitfall 1: Mixing `=` and `<=` in the same block

```verilog
// Don't do this
always @(posedge clk) begin
    a = b;     // blocking
    c <= a;    // non-blocking
end
```

### Pitfall 2: Driving the same variable from multiple `always` blocks

```verilog
// Don't do this
always @(posedge clk) q <= d1;
always @(posedge clk) q <= d2;   // multi-driver: undefined / unsynthesizable behavior
```

### Pitfall 3: Incomplete combinational assignments (unintended latch)

```verilog
// Latch inferred: y holds its old value when sel == 0
always @(*) begin
    if (sel) y = a;
end

// Fixed: always assign a value
always @(*) begin
    y = 1'b0;          // default
    if (sel) y = a;
end
```

### Pitfall 4: Using `#0` delays to "fix" races

```verilog
// Don't: hides the problem instead of fixing the coding style
always @(posedge clk) #0 q1 = d;
```

### Pitfall 5: Using `$display` to check non-blocking values

`$display` runs in the Active region, so it prints values **before** the NBA update. Use `$strobe` (or sample on the next clock) to see settled values.

```verilog
always @(posedge clk) begin
    q <= d;
    $display("display: q=%b", q);  // OLD value
    $strobe ("strobe : q=%b", q);  // NEW value (after NBA)
end
```

## 9. Guidelines Checklist

| Rule | Assignment Type | Target Context | Reason |
|---|---|---|---|
| Sequential logic | Non-blocking (`<=`) | `always @(posedge clk)` / `always_ff` | Prevents simulation races; accurately models physical D-FF sampling. |
| Combinational logic | Blocking (`=`) | `always @(*)` / `always_comb` | Ensures immediate propagation of signals across expressions within the same delta cycle. |
| Latches | Non-blocking (`<=`) | `always @(*)` with intentional latch / `always_latch` | Latches are storage elements, so treat them like sequential logic. |
| Mixed assignments | **Never mix** | Same `always` block / signal | Avoids race conditions and undefined tool behavior. |
| Multiple drivers | **Never** assign one variable from multiple `always` blocks | Whole module | Avoids race conditions and multi-driver issues. |
| Delays | Avoid `#0` | RTL code | Hides races rather than fixing them. |
| Debug printing | Use `$strobe` for NBA values | Testbench | Shows values after the NBA region. |

## Q1. Can we use blocking assignments in a clocked block?

**Answer:** Syntactically yes, and the tools won't give an error. But we **shouldn't**, because it can cause a **simulation race condition** and a **simulation vs. synthesis mismatch**.

---

## Q2. What is the core difference between `=` and `<=`?

**Answer:**

| Operator | Name | Behavior | Next line sees |
|---|---|---|---|
| `=` | Blocking | Updates the variable **immediately** in the Active region | The **new** value |
| `<=` | Non-blocking | Evaluates the RHS in the Active region, updates the LHS **later** in the NBA region | The **old** value |

```verilog
// Blocking: b reads the NEW a
a = 1;
b = a;     // b gets 1

// Non-blocking: b reads the OLD a
a <= 1;
b <= a;    // b gets a's previous value
```

---

## Q3. Give an example where blocking breaks in a clocked block

**Answer:** Two flops in separate `always` blocks:

```verilog
always @(posedge clk) q1 = d;    // Flop 1
always @(posedge clk) q2 = q1;   // Flop 2
```

At `posedge clk`, both blocks trigger in the same time step. The Verilog standard does **not** define which runs first:

- **Flop 1 first:** `q1` becomes `d` immediately, and Flop 2 reads the **new** `q1`. `q2` gets `d` in the same cycle, so it behaves like **1 flop**.
- **Flop 2 first:** `q2` reads the **old** `q1`, so it behaves like **2 flops**.

The result depends on the simulator, its version, or even file order. That is a **race condition**.

---

## Q4. How does non-blocking fix it?

**Answer:**

```verilog
always @(posedge clk) q1 <= d;
always @(posedge clk) q2 <= q1;
```

1. **Active region:** both RHS values are sampled (`d` and the **old** `q1`).
2. **NBA region:** both LHS values are updated together.

Whichever block runs first, `q2` always gets the old `q1`. The behavior is deterministic and matches real flip-flops.

```text
 One simulation time step
 ┌──────────────────────────────────────────────────────────┐
 │  Active Region                                           │
 │   • blocking (=) assignments execute & update NOW        │
 │   • RHS of non-blocking (<=) is evaluated (LHS unchanged)│
 ├──────────────────────────────────────────────────────────┤
 │  NBA Region                                              │
 │   • all scheduled (<=) LHS updates happen here           │
 └──────────────────────────────────────────────────────────┘
```

---

## Q5. Does the synthesis tool complain about blocking assignments? Why not?

**Answer:** No. Synthesis tools infer hardware from **edge sensitivity and data flow**, not from simulator event ordering. `@(posedge clk)` means flip-flops, and `q1` feeding `q2` means a 2-stage chain. So **both versions synthesize to 2 FFs**.

---

## Q6. So where is the actual problem?

**Answer:** Not in the flip-flop count. The problem is a **simulation vs. synthesis mismatch**:

| | Blocking (`=`) | Non-blocking (`<=`) |
|---|---|---|
| **Hardware (synthesis)** | 2 FFs | 2 FFs |
| **Simulation** | 1 or 2 FFs (random) | Always 2 FFs |

The RTL simulation may pass with behavior that doesn't match the hardware that actually gets built.

---

## Q7. Why is the "stale" value the correct one for sequential logic?

**Answer:** A real flip-flop samples its input **before** its output changes (clock-to-Q delay). The next flop must therefore see the **old** output. Non-blocking models that. Blocking would act like a wire, passing the new value through, which is wrong for a register.

| Modeling | Use | Real-hardware analogy |
|---|---|---|
| Registers | `<=` (reads the old value) | A flop samples its input before its output changes |
| Wires / gates | `=` (reads the new value) | A gate output is available immediately to the next gate |

---

## Q8. What if everything is in the same `always` block? Is blocking still a problem?

**Answer:** There is no race, because statements in one block run in written order. But the values now depend on **line order**. Starting from `a = b = c = 0`:

```verilog
// Order 1: a gets old b, b gets old c  -> 3-stage chain
a = b;
b = c;
c = 1;
```

```verilog
// Order 2: each line sees the updated value -> all become 1 on the first edge
c = 1;
b = c;
a = b;
```

```verilog
// Non-blocking: order does not matter -> 3-stage chain
a <= b;
b <= c;
c <= 1;
```

| Clock edge | a | b | c |
|---|---|---|---|
| start | 0 | 0 | 0 |
| 1 (non-blocking / Order 1) | 0 | 0 | 1 |
| 2 (non-blocking / Order 1) | 0 | 1 | 1 |
| 3 (non-blocking / Order 1) | 1 | 1 | 1 |
| 1 (Order 2) | 1 | 1 | 1 |

Reordering lines changes the hardware with blocking assignments. With `<=`, order doesn't matter, so it is safer and easier to review.

---

## Q9. Then where do we use blocking assignments?

**Answer:** In **combinational** blocks (`always @(*)` / `always_comb`), where a wire-like, immediate update is exactly what we want:

```verilog
always @(*) begin
    tmp = a & b;
    y   = tmp | c;   // needs the NEW tmp
end
```

---

## Q10. What are the coding guidelines?

**Answer:**

1. Sequential logic: use **non-blocking** (`<=`).
2. Combinational logic: use **blocking** (`=`).
3. **Never mix** both in the same `always` block.
4. Never drive the same variable from **multiple** `always` blocks.
5. In SystemVerilog, use `always_ff` and `always_comb`. Tools then check your style.

```systemverilog
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) q <= '0;
    else        q <= d;
end

always_comb begin
    y = a & b;
end
```

---

## Q11. One-line summary?

**Answer:**

> *"Blocking assignments in a clocked block make the result depend on execution order, so simulation can differ from the synthesized flip-flops. Non-blocking assignments sample the old values at the clock edge and update afterward, which matches real hardware."*
